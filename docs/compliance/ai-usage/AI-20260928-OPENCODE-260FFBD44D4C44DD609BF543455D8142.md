### 我自己的三个 CRITICAL 缺陷 —— 都由本轮启动的对抗评审实测抓出

启动三个 subagent（合同 COMMIT 调研 / 对抗评审 / 旧 harness 迁移）。对抗评审给出
的发现我逐条**自己复核**后才动手，其中三条是真的，且第一条**与被关闭的 PR #99 是
同一个错误模式**。

**C1：`_export_toolchain` 是 `host_toolchain.derive_kicad_slice` 的平行重实现。**
我写了 100 行去重新派生 KiCad slice，而规范派生器就在仓里、已经 import 过。后果是
**摘要分叉**：规范的 `_resolved_files` 迭代 `sorted(declared)`，我那份按宿主声明的
列表顺序迭代，而 `canonical_json_bytes` 排序 dict 键但**不排序列表** —— 行序因此进入
`canonical_sha256("toolchain", ...)`。`validate_host_binding` 只要求解析映射与声明路径
**集合相等**，所以逆序声明是合法的，于是：

| 两条库逆序声明的合法 binding | toolchain 摘要 |
|---|---|
| `pipeline._export_toolchain` | `5e2fae1f1987383e…` |
| `host_toolchain.derive_kicad_slice` | `414e7c5512af86f1…` |

回执存在的目的正是要满足 `same_host_toolchain`，而它会因此**拒绝一次合法轮次**。
我那份还静默丢了四项规范路径做的校验（`kicad_version` 钉版、超时上限、manifest
绝对路径/角色检查、自校验）。修法是删掉 100 行、改调规范派生器（-6769 字符）。

**与 #99 同型**：#99 是另建一条证据通路而不是调 `verify_stage`，C1 是另建一个 toolchain
对象而不是调 `derive_kicad_slice`。两次都是「平行对象代替仓库自己的对象」。

**C2：recheck 守卫的顺序摧毁了合同第 373 行的状态映射。** 我先写的版本把
`recheck != PASS` 放在 `thin.status != PASS` **之前**。但 `verify_stage` 只有在两次导出
都 PASS 且 coverage/parser 完整时才填 `reports`，其余一律是 `None`，而
`recheck_reports` 对非 mapping 一律 FAIL —— 所以该守卫对**每一个非 PASS 结论恒真**。
实测（真实 verifier、真实请求）：

```text
real verify_stage status : TOOL_ERROR   ("the pinned kicad-cli binary is missing")
real recheck status      : FAIL        ("the receipt carries no reports manifest")
HEAD  发布                : ROLLBACK / cause=TOOL_ERROR   ← 正确（373 行）
当时发布                 : ROLLBACK / cause=BLOCKED     ← 错误
```

第 373 行的另两个桶（`TOOL_ERROR`、`UNKNOWN`）因此变成不可达死代码。**这个缺陷只有
驱动真实轮次才看得见** —— 我原先命名去抓它的测试只测映射表、不跑轮次，变异检验立刻
报 `WRONG`。已补 `test_a_non_pass_verdict_publishes_its_own_cause_not_the_rechecks`。

**C3：冻结失败会吞掉验证器真正的理由。** 冻结无条件跑在状态分支之前，所以一次 I/O
失败会把验证器自己的 `REPAIR_*` 原因替换成通用 `REPAIR_TOOL_UNAVAILABLE`。改为：冻结
失败被**记录**（`freeze_error`），验证器自己的原因仍然发布。
