- 根因：三处各自解析 `akcli`。`gates/run_gates._find_akcli()` 有 `$AKCLI` → PATH → 默认
  三级兜底；而 `tools/repairbench.find_akcli()` 与 `tools/repairbench_synth.AKCLI`
  **只认** `Path.home()/AppData/Local/hermes/hermes-agent/venv/Scripts/akcli.exe`
  （个人 Windows 布局）。
- 更深一层：`test_guard_refuses_the_unsafe_write` 断言的是**写入器的拒绝文本**里含
  `strict-nets`。工具不存在时它先撞到 `pinned akcli writer not found`，于是断言失败的原因
  与守卫毫无关系。含义必须说清：**「`--strict-nets` 到底有没有传给写入器」这件事，
  此前只在持有该个人二进制的单一台机器上被间接验证过，在 CI 上从未被验证过。**
- 修法：
  1. `tools/akcli_identity.py` 独占查找顺序与失败文案：`$AKCLI` → PATH → pin 默认，
     缺失时列出**所有试过的路径**（不再出现 `~` 拼出来的假路径当事实）。
  2. 守卫改成任何平台都能跑的确定性断言（stub 写入器）：guard on ⇒ argv 含
     `--strict-nets`；guard off ⇒ 不含；写入器拒绝 ⇒ 冒泡为 `LlmUnavailable` 且消息含
     `strict-nets`、不含计数字段。
  3. 真正依赖写入器的测量类测试保留，但改为**带行动指引的显式 skip**
     （理由里写明设 `AKCLI=<absolute path>` 与已试路径），替换掉
     `"akcli not available"` / `"frozen board or akcli unavailable"` 这类无法据此修复的泛化说法。
