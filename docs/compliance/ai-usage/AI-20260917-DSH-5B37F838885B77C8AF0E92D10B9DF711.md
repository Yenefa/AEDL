### 起因：被验判据自身写错（不是为了让某条通过而放宽）

冻结判据 §C4 的 C4-P3 行原文：

```text
| **C4-P3** | 走 API 路径且 `tool.tool_applied=null` | 不得当成成功 |
```

它把「API 路径没有 `applied` 字段」这一**设计事实**当成了失败依据。而 PR-1 实现合同 §8 明文规定：

- L253：「exception 在固定 Python worker 内只调用 `akcli.writers.kicad.apply(...)`…**API 原生没有 applied 字段，回执 `tool_applied=null`；不能伪造 true。**」
- L255：「STRICT 只有 exit=0、标准 draw-result、**applied=true**、op_results 完整且全 ok、源 bytes 改变并成功重读时才返回 `APPLIED_TO_STAGE`…**exception 同样要求每个 op ok、真实字节改变及重读成功；不能用 API list 非空作为成功条件。**」

即：`applied=true` 是 **STRICT 路径**的合取项；API 路径上 `tool_applied` **必须为 `null`**（adapter 对该路径 `tool_applied is not None` 反而报 `REPAIR_TOOL_PROTOCOL_ERROR`）。两者安全等级不同，判据把它们混用了。

**反向证据检索（刻意做敌意核对）**：在合同中全文检索「不得当成成功 / 不能当成成功」→ **零命中**；没有任何一处规定 API 路径的 `null` 本身必须导致失败。两处可能被断章取义的文本都不支持反读：L425 是**测试用例清单**（不是谓词，且其条目顺序把「applied 缺失/false/假 true」归入 strict 回执那一组）；L371 的「applied 矛盾」指**矛盾**（如 applied=true 而字节未变），而 L253 已确立 `null` 是该路径**非矛盾**的设计值。结论：矛盾是干净的。
