### 起点是一个被自己推翻的假设

我原本说 SNAPSHOT 的动机是一个「洞」：授权绑定到 candidate 的 `base_source_sha256`，
而 BEFORE 从 stage 读，两者之间没有任何交叉校验。**探针脚本直接印了一句
`HOLE CONFIRMED`，而数据否定了它。**

三次探针，只有第三次公平：

| 尝试 | stage 内容 | 结果 | 实际证明了什么 |
|---|---|---|---|
| 1 | 破坏过的字节 | `UNKNOWN` | 什么也没证明 —— 只是文件不可解析 |
| 2 | DC-05 fixture | PRECHECK `BLOCKED` | 什么也没证明 —— DC-04 **选择器**拒绝 DC-05 |
| 3 | DC-04 改一个 value（DC-04 仍适用） | **STAGE_APPLY `BLOCKED`** | **绑定是真的** |

第 3 次的原文：`the stage bytes are not the proposal base source: the proposal is
stale for this artefact`。

**没有洞。** 绑定由 adapter 强制。我只有去读真实 reason、没有相信自己脚本的
verdict 行才发现这一点 —— 而那句 `HOLE CONFIRMED` 是我硬编码的。
这与本会话一直在防的失败模式完全同型，我却在它上面摔了一跤。

**因此 SNAPSHOT 的动机不是补洞，而是补 C3 缺的生产者**（下面）。

有校验器、有验证器，**没有构造器**，所以 C3 的 snapshot 那一半根本喂不进去。

### 实现

1. **`build_file_manifest(root, target_relative)`** —— 走真实目录，产出 manifest。
   形状不是我发明的：测试**直接调用仓库自己的 `_manifest`** 来证明它被接受，
   并用 5 个负控制证明那个校验器不是来者不拒。逃逸路径与链接一律拒绝。
2. **`materialise_snapshot(...)`** —— 把 candidate 的 design 树复制成 snapshot，
   **逐文件比对字节相同**后才建 manifest，因此截断的副本在这里就失败，
   而不是被描述成有效的 snapshot。落在 candidate 内部则拒绝。
3. **`run_round` 驱动 SNAPSHOT** —— 快照落在 `repair_root/snapshot`（fail-closed：
   没有 repair_root 就拒绝，不自己编一个位置），stage 由 snapshot 播种，
   op-list 跨过播种保留。
4. **BEFORE 改从 snapshot 读** —— 这是 `run_round` 的契约变更，也是本 envelope 唯一
   标为 `contract_change: true` 的地方。理由与「不拆成两版」写在 envelope 里：
   建一个没人读的 snapshot 就是第三个「叙述与配置不一致」。

### 过程中的自造错误（数量偏多，如实记录）

1. `raise RepairContractError("...")` —— 该异常接的是 **findings 序列**不是字符串，
   且它是 `ValueError` 子类，所以失败是**静默**的。已全部改为 `ProposalInvalidError([_finding(...)])`。
2. 阶段顺序一度是 `['SNAPSHOT','PRECHECK','STAGE_APPLY']`（合同顺序的**反面**），
   且在任何 writer 存在之前就复制了文件。已改为 SNAPSHOT 在 bind_policy 之前、
   授权针对 snapshot 的观测签发。
3. **stage 播种把自己的 op-list 删了**，错误信息伪装成「调用方的文件缺失」。
   改为**播种前**把 op-list 读进内存、播种后写回。
4. `str(exc)` 把拒绝原因压成裸 reason code，**丢掉了「哪个字段错了」** ——
   而那正是调用方唯一能行动的信息。已改为透传 `exc.findings`（两处）。
5. `_round_request` 手搓的 host context **缺 12 个字段**，`validate_host_context` 直接拒，
   于是所有 snapshot 测试观察到的都是一次 PRECHECK 拒绝而非 snapshot。
   已改用模块自带的 `host_context()` 真 helper。
6. snapshot 测试用了 `ops: []`，而 `parse_proposal` 要求 **1..8 个 op**。
7. 一次重建 `run_round` 头部时**把函数签名和 docstring 一起丢了**（它们落在被替换区间内）。
   已从**已提交版本**恢复，而不是重打一遍。
8. e2e harness 的 `txn_id` 含空格，不满足 `^[A-Za-z0-9_-]{1,64}$`。

**第 5、6、8 条都是同一个形状的重复出现**：我写了一个只在我脑子里成立的夹具，
然后用「测试绿了」当证据，而它绿在了一个我根本没测的路径上。
这一轮至少有 4 个测试/夹具在变异检验或真实运行中才暴露出「通过的理由不是声称的理由」。

### 开 PR 前的删除行审计（`-31` 行逐行核对）

按指示，在开 PR 前把 `run_round` 被删的每一行归类。**审计脚本本身抓出两个真实缺陷**，
都不是靠读 diff 判断的：

| 类别 | 行数 | 含义 |
|---|---|---|
| RELOCATED | 12 | 同样的代码在 `run_round` 别处仍存在 |
| REPLACED | 9 | 有意且已声明的契约变更 |
| DEDUPED | 6 | 完全相同的重复实现，去重后仍各存一份 |
| COMMENT | 4 | 不再描述代码的注释 |

**缺陷 1：containment 检查有两份，其中一份是死代码。**
第一份 `resolve()` 并 `relative_to()` 校验了一个 `target_path`，然后**再也不读它** ——
因为 BEFORE 已经改从 snapshot 读。唯一真正的读取在 `after_raw = target_path.read_bytes()`，
用的是第二份的值。一份只能拒绝、永远不能放行的检查不是第二道守卫，是第二个要看的地方。
已删除，并留注释说明为何不再重复。

**这一类缺陷测试抓不到，按构造就抓不到。** 能观察到的行为在「死代码存在」与
「死代码不存在」两种情形下完全一致，所以恢复它的变异对测试套件不可见。
这一类的工具是审计脚本，不是测试 —— 13/13 不代表覆盖了它。

**缺陷 2：snapshot 读取失败的消息被我自己的重构弄丢了。**
快照块原来把 `RepairContractError` 与 `OSError` 一起 catch 并用 `str(item)` 格式化，
于是读失败只剩一个 `[Errno 2] No such file...`，不说是哪一步失败。
而这三步（复制树 / 播种 stage / 从 snapshot 读 BEFORE）**都是我们自己的操作**。
本轮早先已经吃过一次这个亏：stage 播种把自己的 op-list 删了，唯一的报错是
「文件缺失」，看起来像调用方的错。已拆成两个 handler，OSError 明确指出三步中的哪一步。

修完新增 T12 变异（把消息改回裸 errno），被 `test_an_unreadable_snapshot_says_which_operation_failed` 捕获。

**该测试自己错了两次才写对**，如实记录：
1. 第一次按 `self.root / "repair"` 比对 snapshot 路径，而 `host_context()` 实际推导的是
   `<root>/.repair` —— 删除从未发生，测试是在断言一个跑完了的轮次。
2. 第二次删掉 snapshot 的 target，结果 stage 播种（stage 由 snapshot 播种）
   先失败，撞上另一条拒绝分支 —— 测的根本不是「读」。
改为把 `Path.read_bytes` 限定在 snapshot root 内抛错，才真正命中读这一步。
