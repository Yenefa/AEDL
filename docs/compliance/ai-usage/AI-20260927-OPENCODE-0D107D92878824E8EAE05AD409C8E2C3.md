### 背景：一次真实的误判，以及它真正的成因

第一笔真实 transaction（DC-04）完成后，我的验证脚本报出
`authorized_delta_match FAIL`（expected `69877d3e…` vs actual `a9e87dea…`），
并据此得出「缺少 post-write identity reconciliation」的结论。

动手写 ADR 前先复核 C2 源码，发现该能力**早已存在**：

```text
gates/repair_verification.py
  _label_semantics(node)        L418  从真实 AST 反解 label 4-tuple

  _canonicalize_new_objects()   L461

  _prepare(...)                 L561  调用 _align_new
  compare_delta(...)            L660  公开验收入口
```

误判成因：脚本绕过冻结入口，直接用底层 `observation_delta()` 自行归一化并比较摘要。
`_align_new` 从未执行，于是 `new:R9` 与 writer 真实 UUID `e51b8115…` 被判为不同对象。

用冻结入口重跑真实 transaction：`compare_delta` **PASS**，
`authorized_delta_sha256 == actual_delta_sha256 == 69877d3e…`，missing 0、unexpected 0。

**因此 Agent 拒绝撰写该 ADR**：其前提为假，写入会把不存在的架构缺陷固化为决策。

### 本次改动（1 个文件，纯测试 +163/-1）

`tests/test_repair_pipeline.py` 新增 `PostWriteVerificationContractTests`（10 例）：

1. `compare_delta` 接受 writer-realized 修复，authorized/actual 摘要相等；
2. 两套 identity 世界确实不同（否则下面几条什么也证明不了）；
3. **naive 摘要比较 ≠ 验收入口** —— 同一对数据上两条路径结论不同（把踩坑固化为可执行断言）；
4. 未授权的 label rotation 必须被拒；
5. 未授权的 component position 必须被拒；
6. component 被移除必须 fail-closed（`UNKNOWN`，绝不为 PASS）；
7. **AST 断言**：`tools/repair_pipeline.py` 中 `observation_delta()` 的调用点所在函数集合
   必须**精确等于** `{_bound_policy}`（仅 expected 侧），任何新增的 post-write 手搓比较都会失败；
8. C5 不得 shadow `compare_delta` / `_align_new`；
9. 验收入口归属 C2（`__module__ == "gates.repair_verification"`），C5 不得重绑定。

第 7 条是本任务的核心：它把「验收入口不可绕过」从约定变成可执行约束。
