### 起因：同一类事故发生了两次

1. **PR #61（Yenefa 侧）**：预注册的 `AEDL_W1_Y4_AI_vs_Script_实验方案.md` 被整份写成 CRLF，diff 从真实的 43/40 膨胀为 245/242。评审作为 M1-2 提出，她已复位为 LF。
2. **本仓库自身（2026-09-12，Percy 侧）**：AI 用 Python `write_text` 更新 `AI_USAGE_SUMMARY.md`，Windows 默认换行转换把整份 345 行文件写成 CRLF，diff 一度为 +355/-345；随后用 `write_bytes` 修回。

两次都不是手滑，而是 **Windows 上工具链的系统性陷阱**：任何按文本模式写回的脚本都会顺手把整份文件变成 CRLF。后果有二——diff 变成全文件重写、无法审阅；文件 sha256 漂移，而本项目的冻结承诺（A3 rubric、B5 判据、证据清单）正是以文件哈希为准。

`core.autocrlf=false` 是本仓库的环境要求，它只保证 Git **不主动**转换，**不会**在有人写入 CRLF 后纠正回来。

### 本次改动

- **`.gitattributes` 新增一行 `*.md text eol=lf`**（附说明注释）：Git 在 `add` 时把 .md 规范化为 LF，即使写入方是 Windows 工具。
  - 放在既有 `text eol=lf` 段落末尾、`delivery/gerbers/* text eol=crlf` 之前；两条规则路径不相交，**Gerber 的 CRLF 不受影响**（交付 ZIP 与清单绑定的就是 CRLF 字节）。
- **`AGENT_ONBOARDING.md` 一次性归一化为 LF**：全仓库 167 个 .md 中它是唯一带 CRLF 的；不先处理，它会在下次任何人改动时产生一次意外的全文件 diff。
