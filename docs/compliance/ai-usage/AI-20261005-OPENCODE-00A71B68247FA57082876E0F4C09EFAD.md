- **发现 1（合同完备性缺口，DC-03/04/05 全灭）**：合同里 `ESP32_GPIO9_PULLUP` 写的是 `"components": {"R9": {"value": "10k"}}`，但这三集的故障正是 **R9 / R7+R8 / C5 整个器件不存在**。机械臂据此推出「给 R9.1 加 +3V3 标签」，akcli 依法拒绝：**exit 6**、`pin reference 'R9' matches no placed component`。结论：合同能完整指定「已存在器件的某个脚接哪个网」，但**不能指定「这个器件应被放上去」**——缺存在性、footprint、坐标。这是合同的缺陷，不是机械臂的缺陷。
- **发现 2（并网风险，DC-01，且被护栏抓到）**：机械臂对 DC-01 加两条标签后，akcli 接受并写入，结果 `net USB_DM: expected ['R8.2','U1.13'] observed ['R7.2','R8.2','U1.13','U1.14']`、`net USB_DP: expected [...] observed []`——**DP 与 DM 并成一网**。原因是本次调用**未加 `--strict-nets`**。该错误被 **Regression Guard + structural 两层同时抓住**（`structural: fail`）。工程结论：**任何按合同推导标签的臂都必须带 net-split 守卫**，否则「修 A 弄坏 B」。
- 8 条回归把上述两条发现 + 对照性质钉死：① 合同每条器件断言只有 `value` 字段；② 每条器件断言必伴随该器件的脚断言（故合同对器件的唯一把手是脚上的网名）；③ DC-03/04/05 机械臂确实无法 primary PASS（若将来合同补上存在性，该用例会失败=缺口已闭合的信号）；④ DC-01 的并网现象仍在（若加了守卫，该用例会失败=风险已闭合）；⑤ 并网必须被 structural 判 fail；⑥ noop 不得通过；⑦ 每集起始必须真的带故障（否则 FAIL→PASS 不成立）；⑧ 合同须通过冻结校验器。这些是**对实测现状的钉住**，不是对期望状态的断言——已在测试 docstring 里写明。
