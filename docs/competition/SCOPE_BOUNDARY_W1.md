## 2. 角色与判断纪律（重写，取代 #37 §5）

### 2.1 旧规则为什么废止

#37 §5（及 master 上的 `W1_CARD_Percy_20260907.md`、`W1_TASKS_20260907.md`）写的是
「**Percy = 独立验收侧，不碰实现代码**」。该表述已被 2026-09-06 至 09-09 的实际事件推翻：

| 事件 | 与旧规则的冲突 |
|---|---|
| PR #41 — 修复 `tools/build_board.py` 的 U3 封装漂移，新增 `tests/test_build_board_footprints.py` | 验收侧写了实现代码与测试代码 |
| PR #46 / #47 / #48 / #50 — 验收侧对四个代码 PR 提交正式 review 并批准 | 验收侧对实现做了放行决定 |

规则与既成事实不符时，应改规则，不应假装事实没发生。

### 2.2 现行纪律：隔离的是「谁写答案」，不是「谁写代码」

**两侧都写代码。** 唯一**不可交叉**的是**期望答案的作者身份**：

| 产物 | 所有者 | 另一侧的权限 |
|---|---|---|
| 器件事实目录、开发案例、期望修复与判定（P3 / P4） | **验收侧** | **只读 + 可提意见，不得直接编辑** |
| 修复实现、验证器、pipeline、门禁（PR-1 C1/C2 及之后） | **实现侧** | **只读 + 可提意见，不得直接编辑** |
| 双方各自的测试代码 | 各自 | 可审可评 |

**非对称的原因**：若实现侧可直接改期望答案，答案会向实现漂移，验收就失去独立性；
反之亦然。提意见的一方负责**报告**，改不改由所有者决定——这与交叉审查中
「作者闭环、审查者复验」是同一条原则。

### 2.3 隔离应当是结构性的，不是自觉

PR #50 给出了本项目应当推广的样板：`gates/repair_verification.py` **只 import 标准库、
不含任何文件 I/O**，因而在结构上不可能读到 `tests/fixtures/repair_pr1/private/` 下的
验收答案；私有答案集只被测试消费。

**判据**：一项隔离若只能靠「约定不去看」维持，就应视为未隔离。可行时应做成
「即使想看也读不到」，并用扰动测试证明该防线承重（把防线削弱后必须有测试变红）。

### 2.4 跨人操作需先问

- 推提交到**对方的分支**：每次都要先问，即使改动很小、即使此前有过类似授权。
- 关闭 / 合并**对方的 PR**：同上。
- 上述两条不因「这样更快」或「对方在睡觉」而豁免。

### 2.5 审查以正式 review 记录为准

交叉审查的结论应提交为 GitHub 的 **Approve / Request changes**，而非普通评论。
以评论形式给出的审计不进入 review 状态，在页面上等同于「未审」，
将来若启用分支保护也不会被计入。

> 说明：GitHub 不允许 PR 作者账户批准自己的 PR。作者本人的独立复核只能以 COMMENT
> 记录（先例：PR #50），此时仍需另一方的正式 Approve 才算完成交叉审查。
