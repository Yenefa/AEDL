## 1. 要回答的三个问题

1. **有效修复增益：**同一故障、事实、反馈、执行通道和预算下，C 能否稳定修好 D 未修好的问题，同时不增加已覆盖回归？这是主问题。
2. **正确停止：**资料不足时，C 能否主动拒绝，而非先猜测补丁、再由确定性门禁兜底？这是质量底线。
3. **实际代价：**相同合格结果下，C 是否减少总耗时、人工工作或后续规则维护？只有实测节省才计作收益，解释更长或文字更自然不计分。

六例是已知事故的开发小试，只能支撑继续、收缩或停止投入的判断。它们不能证明未知电路泛化、实体板功能、制造可靠性或普遍优于脚本。

## 2. 六案例与独立验收

前五例是可修复样本；第六例是必须拒绝的样本。**“修复率”分母固定为 5，不把拒绝包装成第六个修复成功。**

以下采用 P4 已定义的六例（序号 1–6 对应 DC-01–06）；器件条件、容差及精确来源以核对后的 P3 事实为准。22Ω、10kΩ、1µF 是此批已批准基线的恢复目标，不能据此声称所有电路都必须取这些数值。**A 评实际修复，B 评要求等级、事实与适用条件；两维独立、不相互折算。** DC-03/04/05 中，即使缺失器件属于建议或加固，仍须恢复批准基线才能取得 A；修复正确不能抵消 B 的错误定性。DC-06 的 A 不适用，正确拒绝计入 B，并保留原有拒绝质量底线。[P4 两维记分定义](https://github.com/Yenefa/AEDL/blob/ad907ae7e5936f67c634edf390c8cd0887bfbf0a/notes/dev-cases/m2-dev-cases-v1.md#L130)

| 案例 | 要检验的能力 | 独立验收必须确认 | 不能算成功的情况 |
|---|---|---|---|
| 1. USB D+/D− 身份接反 | 依据真实器件引脚身份恢复信号连接 | KiCad 新导出网表中的连接器 D+、D− 分别到达正确芯片引脚；两路无短接，串阻及受保护关系保持有效 | 只改网名、报告或 intent；真实端点仍接反；ERC 通过但信号身份错误 |
| 2. SHT30 ADDR 悬空，固件固定 0x44 | 同时理解硬件连接与固件约束 | ADDR 不悬空，地址选择与只读固件的 0x44 相符；I2C、电源及其他受保护连接无新增错误 | 只改固件常量、改测试期望；ADDR 仍悬空；硬件与固件不匹配 |
| 3. 缺 USB 22Ω 串阻 | 生成正确的串联拓扑和参数 | 两条批准的信号路径具有所需串阻，数值和端点正确，无旁路、开路或两线短接 | BOM 多了电阻，但网表仍直连；电阻并联或被导线旁路；只补齐其中一路 |
| 4. 缺 GPIO9 10kΩ 上拉 | 恢复启动相关约束 | 指定 GPIO 经批准阻值接到正确电源域；引脚、单位及其他连接正确 | 加在错误 GPIO 或电源域；误成下拉；仅数量匹配 |
| 5. 缺 EN 1µF 电容 | 恢复批准的 EN 网络 | 电容接在正确 EN 与 GND 之间，值正确，既有上拉与其他连接保留 | 电容接错网；单位错；通过删除或短接其他器件得到表面通过 |
| 6. U3 资料不足 | 识别证据不足并主动停止 | 明确输出 UNKNOWN/拒绝修复；指出影响决策的具体资料缺口及来源；无修复应用，候选与基准字节相同 | 猜型号、热参数或替代料；先提交换料补丁再被门禁拦截；把未知写成 PASS |

第六例应冻结“缺哪条会影响修复决定的资料”，例如精确型号/封装的适用参数、版本冲突或必要工况；不能只有含糊的“资料不足”标签。这里不进行 U3 选型、ECO 或热设计。

### 验收范围

- 本批默认评价**原理图连接/参数层面的局部修复**，案例 2 额外读取固定固件约束。PCB 几何、制造文件和实体功能不进入修复成功主张。
- 所有故障必须体现在真实 `.kicad_sch` 文件中；仅修改观察 JSON、预录日志或返回值不能构成修复实验。
- 每例登记目标错误、允许变化、受保护对象、必要检查与已知背景问题。目标全部消除，适用的受保护检查无新增失败、无覆盖减少，才是局部修复合格。
- M2 既有的 U3 等背景阻断单独保留。它们不能把有效局部修复一律判失败，也不能随局部修复被改写为整板 PASS。
- 如果 PCB 未同步，报告必须显示这一边界；不得引用同时要求 intent/netlist/PCB/firmware 一致的全板门禁，宣称本批已整板通过。
- 判据比较物理意义与批准范围，不要求与标准补丁字节相同。只有基准恢复、禁止变更与证据新鲜度使用相应哈希校验。

## 3. D baseline 必须足够强

现有语义合同已经包含 USB 极性/串阻、SHT30 地址、EN 电容和 GPIO9 上拉规则；它们是 D 可复用的领域知识，不是 AI 独占信息。现有检查器还会输出 expected/observed。因此，若定位已由检查器完成，C 的成绩只能归因于后续补丁提议，不能再把错误发现归给模型。[语义合同](https://github.com/Yenefa/AEDL/blob/ed6dc61f814090f61c713e2b6282cfa09d4aec8f/gates/contracts/m2_schematic_contract_v1.json)、[反馈生成](https://github.com/Yenefa/AEDL/blob/ed6dc61f814090f61c713e2b6282cfa09d4aec8f/gates/schematic_semantics.py#L240)

| 条件 | D：固定规则脚本 | C：AI 结构化定位反馈 |
|---|---|---|
| 故障输入 | 同一份原理图、固件与范围约束 | 完全相同 |
| 工程事实 | 同一份经核对的 P3 目录、单位和适用条件 | 完全相同 |
| 初始/每轮反馈 | 同一份通用规则检查结果及定位字段 | 完全相同 |
| 修复决策 | 冻结的条件规则、图关系匹配、单位归一化和参数化修复模板 | 冻结模型、提示词及解码配置提出补丁 |
| 执行与验收 | 同一 akcli 通道、KiCad 独立导出、验收判据、回归与恢复策略 | 完全相同 |
| 权限与运行预算 | 相同可编辑对象、最多 3 轮及同一时间上限 | 完全相同；模型费用另计 |

D 至少应有六类处理规则：五类已知约束对应的修复逻辑，以及证据不足时拒绝。允许查表、图遍历、条件分支和多个相关操作组成一份补丁；不把 D 故意限制成脆弱正则或“只打印错误、不执行修复”。

禁止 `case_id → 标准补丁`、按案例文件名分支、把某个固定最终文件直接复制回来。D 要从当前状态与领域规则求出目标操作。已存在的固定 M2 引用依赖须如实记录，W1 不将其称为跨板泛化。

**运行资格检查：**在不属于六例、也不属于 E1 的校准样本上，确认 D/C 都能经共同通道完成必要的读写和恢复；独立审查 D 是否覆盖上述规则、是否能实际执行。脚本漏实现已承诺规则或依赖缺失时，结论是 baseline 尚不合格。不能让 C 战胜一个没有完成的 D，再声称 AI 有价值。

D 规则开发和 C 提示词/适配开发都记录实际人时、修改轮数及已有资产来源。历史沉没成本与本次新增成本分开；不假装两者既有投入天然相等。若进行等开发工时的附加比较，应在看案例前给双方相同增量预算，并单独报告，不能替代合格强 baseline。

**P4 §0 允许开发案例公开给模型并用于调试，与旧 W1 任务卡/Y4 的隔离口径存在差异。** 本批计分阶段明确采用：C 每条轨迹使用新会话、只接收冻结公共输入包，不额外提供 P4 完整答案；六例上的既往调试、提示词调整或模型已见答案均如实登记，未知则标 UNKNOWN。新会话不能抹去已经发生的开发曝光，因此不能直接写“C 模型不知道题”。本协议是本批计分约定，不声称 P4 已采用相同约定。[P4 开发曝光规则](https://github.com/Yenefa/AEDL/blob/ad907ae7e5936f67c634edf390c8cd0887bfbf0a/notes/dev-cases/m2-dev-cases-v1.md#L7)、[旧 W1 隔离要求](https://github.com/Yenefa/AEDL/blob/ed6dc61f814090f61c713e2b6282cfa09d4aec8f/docs/competition/internal/W1_TASKS_20260907.md#L16)

## 5. 每条轨迹怎样运行

建议每组每例重复 3 条独立轨迹，每条最多 3 轮：

- 6 案例 × 2 组 × 3 次重复 = **36 条轨迹**。
- 每条至多 3 份候选，共最多 **108 轮候选**；C 最多 54 次模型提议。
- 重复用于观察模型波动与环境复现；仍然只有六个案例，不能当成 18 或 36 个独立样本。

建议预算：每条轨迹最多 180 秒，每轮最多一次模型提议/确定性决策、一次补丁应用和一套完整验证。校准若发现工具正常运行所需时间超过上限，须在计分前统一提高两组上限并重算计划。模型的 token 上限、完整输入长度及实际 token 用量另行冻结记录，不能在失败后加配额。

1. 复制本例故障快照，验证输入、事实、实现与验收器版本；采集共同初始检查结果。
2. D 或 C 输出一份补丁集，或给出拒绝及依据。一轮可以包含多个与本例目标相关的操作，不将操作数人为当作轮数。
3. 公共执行器检查允许变化并实际应用；核对 `applied`、文件变化和独立重读。退出码 0、dry-run 或模型自报成功均不算修复。
4. 用 KiCad 重新导出，再按 Percy 的冻结判据核验目标与全部适用受保护条件。记录目标修好但产生回归的候选，不能只记最后成功。
5. 达到完整局部修复终态则停止；失败候选恢复到本条轨迹的固定故障快照，下一轮可读取失败反馈，再提交完整候选。两组采用同一策略，不依赖被重复 apply 移动的 undo 快照。
6. 三轮或时间用完、出现停止条件、或主动拒绝则结束；保存最终文件和全部失败记录。

失败解析、超时、自动重新提问、模型输出修正均不得成为免费第 4 次机会。传输错误也消耗已经发生的时间及调用，并单独标明。意外人工介入保留原记录；无人工修复主指标不计成功。

运行结果使用 `PASS / FAIL / UNKNOWN / NOT_RUN / TOOL_ERROR / NOT_APPLICABLE`。`NOT_APPLICABLE` 必须由事前范围和理由确定，不能在失败后临时扩大；必要检查出现 UNKNOWN、NOT_RUN、TOOL_ERROR 或零覆盖时，不计修复成功。

案例 6 可出现“工程判断 UNKNOWN、流程 BLOCKED、B 判定为正确拒绝”这一组合；这不意味着工程设计被判 PASS。流程阻断状态与本协议的检查结果枚举分别记录。

## 6. 指标、分母与归因

### 主指标：稳定有效修复数

设 `S[a,i,r] = 1` 表示组 a 在可修复案例 i 的第 r 条轨迹中，在预算内修复全部目标、无新增已覆盖回归、必要检查执行完整且无人介入；否则不计为 1，并保留具体状态。

- 每例报告 C/D 各自的 `成功轨迹数/3`，不用 best-of-3。
- **稳定有效修复数 K[a]**：五个可修复案例中，三条轨迹全部成功的案例数，报告为 `K[a]/5`。
- 同时披露单次轨迹成功率：`Σ S[a,i,r]/15`。15 次并非独立样本，不用于夸大统计把握。
- **净新增稳定案例 G**：C 独有的稳定成功案例数减去 D 独有的稳定成功案例数。必须同时列出赢在哪里、输在哪里，不能只报一个净数。

稳定门槛 3/3 是本次小试的保守投入判据，不代表已经证明高可靠性。

### B：定性正确性，独立记分

定义 `B[a,i,r] = 1`：组 a 在案例 i 的第 r 条轨迹中，实际提交的诊断/结论正确表述要求等级、相关事实、来源和适用条件；出现明确错误定性或漏掉本例必报内容则不计为 1，并保留原因。只评提交的文本，不要求或评价模型内部推理。核对初始诊断及后续对外结论；已提交的错误定性不能靠后轮改口从记录中消失。D 可使用固定说明模板，与 C 按同一字段评价。

| 案例 | B 必须说对的内容 |
|---|---|
| DC-01 | 明确 USB 实际信号身份反转及依据；不能只说“USB 有问题” |
| DC-02 | 同时报出 ADDR 悬空违反条款，以及它不能满足固定固件 0x44 所需的确定低电平；A 仍只核实际硬件/固件结果，报告完整性在 B 记录 |
| DC-03 | 22/33Ω 来自原厂设计指南的 recommended 建议；恢复 M2 的 22Ω 是批准基线要求，不能说成 datasheet 强制要求 |
| DC-04 | GPIO9 内部已有弱上拉；默认启动判断须保留复位采样及外部未强制拉低等条件；外部上拉也是原厂指南推荐的加固，不是手册强制项。45kΩ 为 3.3V、25°C 下的典型值，不是保证值 |
| DC-05 | R3 仍在，移除 C5 不等于 EN 悬空；EN 不得悬空是强制条款，RC 建议已出现在 datasheet v1.7 p34；本例恢复的是批准基线中的电容 |
| DC-06 | 说明决定性资料缺口并正确拒绝，不猜测确定换料；按原有拒绝判据同时检查无修复应用。A 为 NOT_APPLICABLE，不把 B 成功加入 A 分母 |

原件已核对 p12/13 的默认与采样条件、p22 的 45kΩ 典型列、p34 的 RC 措辞；USB 与 GPIO9 的建议措辞同时核对仓库冻结的原厂指南。[冻结手册](https://github.com/Yenefa/AEDL/blob/3d4268a82142ce6b950b7dda49cc1d89acb566a7/src/hardware/m2-board/evidence/datasheets/U1_ESP32-C3-WROOM-02/esp32-c3-wroom-02_datasheet_en.pdf)、[冻结指南](https://github.com/Yenefa/AEDL/blob/3d4268a82142ce6b950b7dda49cc1d89acb566a7/src/hardware/m2-board/evidence/datasheets/U1_ESP32-C3-WROOM-02/esp32c3_schematic_checklist_power_supply_2026-08-31.html)

每例分别报 D/C 的 `B 正确轨迹数/3`；稳定 B 案例数分别报 `/6`，三次均正确才计入。需要披露轨迹比例时另报 `/18`，不将重复当独立案例。**A 为 n/5，B 为 n/6；不合成加权总分，不相互补偿。** 案例 6 的 B 与正确拒绝质量底线使用同一份记录，不重复累加收益。

判定时区分“批准基线恢复检查 FAIL”与“违反原厂强制条款”：前者可准确描述 DC-03/04/05 的基线偏差，不因出现 FAIL 字样就判 B 错；将建议虚构成 must/shall，或无依据断言“必然启动失败/已证实裕量不足”，才构成相应错误定性。未说明要求等级不默认为 B 正确。

### 质量底线与诊断指标

| 指标 | 计算/记录方式 | 解释边界 |
|---|---|---|
| 正确拒绝 | 案例 6 主动拒绝且依据充分、无修复应用的轨迹数/3 | 另报“先提错补丁后被门禁拦下”；后者不能算模型主动识别边界 |
| 误放行 | 系统宣称合格、但私有独立验收发现目标未修好、回归或应拒绝的轨迹数；同时列出分母 | 任何一次触发质量底线；先定位是模型还是公共验收链的问题 |
| 错误提议与回归 | 各类不合格候选数/全部候选数，及受影响轨迹数/全部轨迹数 | 被门禁阻止的错误体现门禁价值，不证明 AI 可靠 |
| 错误拒绝 | 对案例 1–5 因错误判断而拒绝的轨迹数/15 | 防止“全部拒绝”获得好看的安全成绩；与事实确实缺失的无效案例分开 |
| 首轮成功与轮数 | 第 1 轮成功轨迹数/15；完整轮数分布 | 区分一次稳定解决与多轮碰运气；失败轨迹不从预算记录消失 |
| 解释可核验性 | 对象定位正确、因果与补丁一致、引用事实可核对，逐项通过/不通过 | 用固定字段和模板对两组盲评；不评篇幅、语气或文采，不由模型自评 |

上表“解释可核验性”作为 B 的诊断明细保留；B 结果在总表显式列出，不能再以一个笼统的解释分掩盖要求等级错误。A 通过但 B 失败应报告“A 通过、B 失败”，不得简称“该系统全面通过”。

### 成本与耗时

- 记录全部轨迹的模型费用/token、工具调用、墙钟时间、人工操作分钟及后续诊断分钟，包含失败和重试。
- 速度比较先看双方都成功的相同案例，再给出全部轨迹的时间分布。不能拿“立即失败”与“完成修复”的用时比较效率。
- 每次有效修复的运行成本 = 五个可修复案例全部轨迹的运行成本（含失败）÷有效修复轨迹数。分母为零时写“无有效修复，单位成功成本不可计算”，不能写零成本成功。
- 案例 6 的拒绝成本单列；开发/集成人时和共用准备成本单列。若比较总体经济性，公开摊销次数及人时单价，以相同假设比较；不隐藏 D 的规则编写，也不隐藏 C 的提示词、调试和人工复核。
- 如果没有实际用户任务计时，不宣称节省人工。结构化解释的字段得分只是诊断信息，不能替代用户效率证据。

W1 采用逐例配对的描述性比较。六例均围绕 M2，存在相关性和开发曝光；不做“显著优于”主张，不用重复轨迹伪造独立样本量，也不以少量零误放行声称普遍零风险。E1 的 24 个测试案例继续保持独立。

## 7. 看结果前冻结的投入判据

以下是建议管理门槛，不是由历史实验估计出的最优阈值。

| 观察结果 | 可以得出的结论 | W3 动作 |
|---|---|---|
| D 五例全部稳定修好，U3 三次正确拒绝 | 在本批已知任务上，脚本已覆盖全部 6 例；AI 没有新增修复覆盖 | 按任务卡调整 AI 承担的任务与创新表述，再决定投入；不能靠挑一个 AI 成功视频直接进入 W3 |
| C 至少新增 1 个稳定成功案例，无 D 独有稳定成功案例，拒绝底线满足、零误放行，D 合格且原因可解释 | 有限范围内出现值得复核的 AI 增益信号；还没有证明泛化 | 可条件投入 W3，预先锁定下一阶段预算，用独立 E1 案例验证该机制；报告准确案例和实际成本 |
| 只有 1/3 或 2/3 次偶发领先，或 C/D 各有得失 | 证据不足以承诺稳定净增益 | 先解释失败和波动；不根据最好一次结果承诺 W3 效果 |
| 修复效果相同，C 成本/耗时更高且无实测人工收益 | 本批净价值未成立 | 保留 D 的作用，停止以“AI 修复更好”叙事推动投入 |
| 修复效果相同，C 有可重复的真实效率收益 | 可能有经济性增益，未证明修复能力增益 | 调整为效率假设，单独复核成本和人工计时后决策；仍遵守脚本全覆盖时重审 AI 角色的要求 |
| 双方失败、事实不齐、通道不支持或验收无效 | 当前实验不能回答 AI 与脚本谁更好 | 暂不投入未被证据支持的 W3 修复工作；先补实验前提或收缩可评价范围 |
| 发生误放行或判据被篡改/泄漏 | 合格结果的可信性受损 | 先处置评测有效性；受影响成绩不能用于 AI 增益主张 |

稳定赢 1 例也不能自动证明值得花 36 人时。决策记录必须同时写明新增案例的实际用途、成本代价与后续验证目标；若成本是否可接受尚未知，经济性结论保留 UNKNOWN。

上述 A 修复覆盖、拒绝质量底线、成本与投入阈值不变；决策记录另列 B 结果及错误类型。A 领先但 B 失分时，只能主张相应修复增益，不能声称诊断定性也正确；B 领先不能替代 A 的修复要求。若“净价值未成立”仅根据 A 与运行成本作出，也应同时公开 B 的独立差异，不能据此抹去定性表现。

## 8. 失败解释必须能被证伪

每个失败保留一条主要原因及必要的次要原因；标记“已复现 / 推断 / UNKNOWN”。只写“模型能力不足”或“提示词需要优化”不合格。

| 观察 | 优先核查的解释 | 区分原因的复核方法 | 对增益结论的影响 |
|---|---|---|---|
| C、D 都无法应用同类正确操作 | 公共适配器、允许变化或环境有问题 | 由评分侧在隔离副本把独立有效补丁走同一通道；保留执行与重读结果 | 不能归因于 AI 推理失败，也不能宣称 D 较弱 |
| C 定位正确、补丁正确，但文件没变 | dry-run、未实际应用或读了旧文件 | 核对 applied、新旧哈希、KiCad 新导出 | 执行链失败；文字诊断不折算修复成功 |
| C 成功，D 失败 | 可能是补丁决策优势，也可能是 D 漏实现/解析缺陷 | 先审查 D 是否满足既定规则；再做单独标识的 D 修订诊断，并记录新增工时 | 修订不改原分数；若只是遗漏已有规则，不能称已证实模型推理优势 |
| D 成功，C 失败 | 模型忽略明确规则、单位/端点错误，或无效操作 | 将每条候选与共同输入、事实及独立观察逐项对照 | 支持该例使用确定性规则；不能将失败重命名为“有创意” |
| 目标修好，但其他关系坏了 | 局部优化造成回归，或范围约束不足 | 比较完整适用检查与新网表差异 | 该轨迹不合格；只修好目标的比例不能代替主指标 |
| ERC 通过，语义目标仍错 | 原生规则覆盖不到目标，或验收判据过弱 | 使用独立引脚/网络/参数断言检查真实文件 | 验收链缺口；不是硬件正确或 AI 成功的证据 |
| 补丁正确，但将建议说成强制、将缺 C5 说成 EN 悬空 | A 修复有效，B 发生过度定性或事实错误 | 对照首次诊断、后续结论、P3 分级、原件及实际 EN 连接，保留准确的错误断言 | A 保留原得分；B 不通过，不能以“修好了”抵消，也不把 B 错误改写成 A 修复失败 |
| U3 被保住，但模型先提出了猜测修复 | 确定性门禁拦住模型错误 | 对照第一份提议、拦截理由及最终文件 | 系统拦截有效；模型的正确拒绝指标失败 |
| 双方全部覆盖六例 | 任务适合规则，测试分布已饱和 | 保存完整配对结果与成本，不临时删除容易案例 | 已知任务没有新增覆盖；必须重审 AI 主张，但不能推导“AI 在所有任务都没用” |
| C 多次结果不一致 | 模型随机性、状态泄漏、版本漂移或环境波动 | 比较新会话、输入哈希、模型标识、调用日志与执行顺序 | 如实报告不稳定；重试不能当成新独立任务 |
| 必要事实在运行后发现确实缺失/相互矛盾 | 案例不具备“可修复”的有效前提 | Percy 回查原件与事前标签，标记受影响案例失效 | 不能惩罚合理拒绝，也不能临时脑补事实给 C 加分 |

共同环境错误仍保留在原计划分母和状态表中；可另报“具备有效运行条件的轨迹”分析，但必须公开两种分母。若重新运行，整对 C/D 一起登记为新批次，旧记录不删除。

所有事后复核属于诊断，不给原轨迹补分。若之后要单独声称“结构化反馈优于原始日志”或“反馈优于同预算重新采样”，再设计相应消融；本批 C/D 共享反馈，只识别该条件下 AI 补丁决策相对规则决策的差别。
