# RAG_DECISION — 是否引入 RAG 的决策记录

> 一页纸决策记录，目的是防止以后重复讨论"要不要上 RAG"。
> 日期：2026-08-31；记录人：AI-20260831-011（依据主会话对真实数据规模的判定）。

## 1. 决策

**2026-08-31 判定：暂不引入 RAG / 向量检索。** 维持现有"结构化 ID 引用 + 按需加载"信息架构（见 `docs/ID_MAP.md`）。

理由三条：

1. **数据规模未到阈值**：全部项目 md 约 42 个 ≈ 14 万 token，现代长上下文一次装得下；接手成本通过 HANDOFF 状态卡（≤15 行）+ 按需加载路由解决，不需要语义检索来省 token。
2. **信息强结构化，精确检索已优于相似度检索**：项目检索几乎全部通过 ID（AI/ADR/EVID/RES/PIT/TASK）与文件路径完成，是精确匹配、精确率 100%；换成向量相似度反而引入"检索到相近但不相关内容"的噪声，还多一条需维护的索引管线。
3. **外部知识走 sha256 精确绑定，严格优于 RAG chunk**：数据手册等外部真值已用"冻结副本 + sha256 + 逐页核对"方式进证据链（第 11 门禁 datasheet_contract）；对工程验证而言，可哈希定位的原件远比向量化的 chunk 可信。

## 2. 重启讨论的触发条件（满足任一条才重新评估）

1. 文档总量 > 50 万 token（约当前 3.5 倍以上）。
2. M3+ 多板并行，出现跨板查询需求（"哪块板用过这个料/踩过这个坑"成为常态）。
3. CircuitBot 生成层接入——它自带 FAISS 器件 RAG，可直接复用而非自建（见 `notes/open_source_intake/circuitbot.md`）。
4. 台账/教训条目涨到数千条，`grep`/ID 定位变慢——届时先用 SQLite 索引，仍不必上向量检索。

## 3. ADR 判定

按 `AGENTS.md` §6 触发清单核对：本决策不改变系统架构、Agent Workflow、Verification Protocol、关键接口/Schema 或安全边界，属于信息架构治理的"普通实现细节"层面。**判定：不立 ADR**，理由：非系统架构/接口/验证协议变更。留人工复核；若人工认为信息架构属于长期治理决策需追溯，可再补立（当前 ADR 序列至 ADR-005，ADR-007 为候选未立项）。
