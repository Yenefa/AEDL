# AEDL 开源项目吸收与再设计策略

> 日期：2026-08-30  
> 用途：AEDL / Autonomous Hardware Engineering Agent 开源生态研究与能力吸收计划  
> 核心原则：**成熟的轮子，直接用；有缺陷的轮子，拆开修；真正没有的机制，集中火力自己造。**

---

## 0. 总体判断

AEDL 现在不应该继续把 CircuitBot、KiCadAI、NeuroBoard、KiCad MCP 等项目单纯视为“竞品”。

更合适的视角是：

> **把它们当作开源能力库和工程经验库。**

自然语言制板、Agent 编排、KiCad 操作、DRC/ERC、器件检索等方向已经出现明显的行业收敛。继续从零重复实现这些成熟能力，意义有限。

AEDL 更值得投入的方向，不是“重新造一个 AI PCB Agent”，而是：

> **系统性吸收现有 AI EDA 的成熟能力，并针对其验证可信度、变更一致性、供应链约束、制造签发与经验闭环问题，重新设计一套更严格的硬件工程 Agent 工作流。**

换句话说：

```text
不是：
“别人做了，我也做一个。”

而是：
“别人哪块做得好，我吸收；
 哪块有明显缺陷，我修；
 哪块没人做实，我自己造。”
```

---

# 1. 第一轮重点研究对象

当前优先研究四个项目：

1. **CircuitBot**
2. **KiCadAI**
3. **NeuroBoard**
4. **KiCad MCP**

它们分别代表四类值得 AEDL 吸收的能力：

```text
CircuitBot
→ Requirement Clarification / LangGraph Orchestration

KiCadAI
→ Capability Boundary / Evidence / Fail-Closed

NeuroBoard
→ KiCad IPC / UI / Event Architecture

KiCad MCP
→ EDA Tool Layer / KiCad Automation
```

---

# 2. CircuitBot：重点吃 Clarify 与编排

## 2.1 值得吸收

CircuitBot 最值得 AEDL 研究的是：

- requirement clarification
- LangGraph 状态机
- conditional edge
- repair routing
- component research / RAG
- multi-stage workflow
- 从模糊自然语言到较明确工程输入的转换

其价值不在于“它也能做 PCB”，而在于：

> **它已经把“先澄清用户需求，再进入设计”做成显式工作流。**

这正是 AEDL 当前值得补齐的一环。

---

## 2.2 不建议直接照搬

不建议直接把以下部分视作 AEDL 的验证基础：

- LLM judge 作为最终裁判
- verification 与 repair 混合过深
- 当前较弱的 PCB physical verification
- 尚未形成完整 DRC-in-loop 的部分
- 单纯把 clarification 结果留在 Agent state / memory 中

---

## 2.3 AEDL 应该怎样重新设计

CircuitBot 给我们的启发是：

> **Clarify First**

但 AEDL 不应该停在“Agent 问几个问题”。

AEDL 应该把澄清结果转化成正式、可追溯、可哈希绑定的工程 artifact：

```text
User Natural Language
        ↓
Requirement Parser
        ↓
Ambiguity Detector
        ↓
Blocking Unknown?
      ↙        ↘
    YES        NO
     ↓          ↓
Minimum Question
     ↓
User Answer
     ↓
Requirements Contract
     ↓
Contract SHA256
     ↓
Intent
```

建议引入：

```text
requirements_contract_v1.json
```

至少包含：

```text
user_goal
resolved_requirements
assumptions
blocking_questions
user_answers
unresolved_nonblocking_items
constraints
forbidden_assumptions
source_statement_ids
contract_sha256
```

### 核心转化

CircuitBot：

> 先问清楚再设计。

AEDL：

> **澄清后的需求形成不可静默篡改的工程合同，并绑定后续 intent / schematic / PCB / firmware。**

这才叫“吸收后再设计”，而不是复制。

---

# 3. KiCad MCP：工具层能省命的全部吃掉

## 3.1 基本原则

KiCad MCP 属于典型的：

> **已有成熟工具层，不值得 AEDL 重复造轮子。**

如果成熟 MCP 已经能稳定完成某个动作，就没有必要为了“自主研发感”重新实现一遍低水平版本。

---

## 3.2 可重点复用的能力

优先研究和复用：

- KiCad project 操作
- schematic editing
- component placement
- routing
- ERC
- DRC
- Gerber export
- BOM export
- CPL / pick-and-place export
- custom symbol
- custom footprint
- JLCPCB / LCSC parts
- pricing
- stock
- Freerouting
- pin-level tracing
- PCB analysis
- pinmux conflict detection
- session / tool logging

---

## 3.3 AEDL 的边界必须非常清晰

工具可以复用。

**判决体系不能外包。**

例如：

```text
KiCad MCP
   ↓
run_drc()
   ↓
raw DRC result
   ↓
AEDL structured parser
   ↓
evidence binding
   ↓
semantic gate
   ↓
fault injection
   ↓
manufacturing decision
```

也就是说：

> **工具可以买，工具可以借，工具可以直接用。**
>
> **但“为什么判绿、为什么判红、这个结果凭什么可信”必须由 AEDL 自己定义。**

---

# 4. KiCadAI：重点吃 Capability Boundary 与 Evidence

## 4.1 最值得研究的思想

KiCadAI 最值得 AEDL 吸收的不是“它也能生成 KiCad”，而是：

```text
Request
   ↓
Capability Assessment
   ↓
SUPPORTED
EXPERIMENTAL
UNSUPPORTED
```

核心思想：

> **不知道就停止，而不是猜。**

这与 AEDL 的 fail-closed 理念高度兼容。

---

## 4.2 AEDL 应该进一步强化

例如用户提出：

> 设计一个 48V / 20A BLDC 控制器。

系统不应该直接：

```text
“好的，正在生成 PCB。”
```

而应该先形成能力判断：

```text
Power-stage topology       EXPERIMENTAL
MOSFET SOA verification    UNSUPPORTED
Gate-driver validation     SUPPORTED
Thermal model              INSUFFICIENT_EVIDENCE

→ STOP
```

然后明确：

> 当前系统缺少足够能力与证据，因此不得声明 manufacturing-ready。

---

## 4.3 值得重点研究

- capability classification
- supported / experimental / unsupported
- capability promotion
- frozen corpus
- content-addressed evidence
- exact-hash approval
- evidence bundle
- minimum blocking clarification
- unsupported fail-closed
- capability regression

---

## 4.4 AEDL 的进一步融合方向

KiCadAI 的 capability system 可以和 AEDL 现有能力结合：

```text
Capability Boundary
        +
Human Gate
        +
Fault Injection
        +
Cross-view Hash Binding
        +
Lessons Registry
        ↓
Bounded Hardware Autonomy
```

目标不是让 Agent “什么都敢做”，而是：

> **明确知道自己能做什么、不能做什么、做到什么程度才能宣称结果可信。**

---

# 5. NeuroBoard：吃产品工程，不吃夸张验证

## 5.1 值得吸收

NeuroBoard 比较值得研究的是：

- KiCad IPC abstraction
- LangGraph + FastAPI
- frontend / desktop integration
- Tauri / React
- agent event streaming
- live design feedback
- engineering task orchestration
- SKiDL / netlist pipeline
- 用户能够实时看到 Agent 在做什么

这些能力对未来 AEDL 产品形态非常有帮助。

---

## 5.2 不应该直接信任的部分

当前对其源码分析显示，以下能力需要谨慎：

- “完整 transactional rollback”
- DRC/ERC 失败后的真正整板事务回滚
- SI 仿真
- PDN 仿真
- mock fallback
- 硬编码作者本机环境的 IPC 路径
- 动态执行 LLM Python 的安全边界

尤其：

> “Atomic commits with rollback on DRC/ERC failure”

不能只看 README。

必须看：

```text
失败时到底恢复了什么？
只恢复 footprint 位置？
还是 track / via / zone / net / metadata 全部恢复？
```

---

## 5.3 AEDL 应该怎么吃

建议：

```text
吃：
IPC
UI
Event Stream
Desktop Integration
Live Agent Feedback

不吃：
弱 SI/PDN 模型
Mock-as-success
不完整 rollback
不明确的验证语义
```

一句话：

> **产品工程层吸收，验证语义自己掌握。**

---

# 6. 统一的“开源项目 Intake 协议”

以后发现任何新的 AI EDA / Hardware Agent 项目，不允许只看 README 后说：

> “卧槽，好牛逼。”

也不能看到一个功能就立刻搬代码。

所有项目统一经过六步：

---

## STEP 1 — CLAIM

### 它声称做了什么？

记录：

- README claim
- 文档 claim
- demo claim
- benchmark claim
- roadmap claim

并严格区分：

```text
Implemented
Claimed
Roadmap
Experimental
Unknown
```

---

## STEP 2 — SOURCE

### 源码实际上做了什么？

必须检查：

- 文件路径
- 核心类 / 函数
- 调用链
- 失败路径
- CI
- tests
- license
- commit SHA

---

## STEP 3 — FAILURE

### 它最烂的地方是什么？

寻找：

- fake success
- mock fallback
- silent fallback
- fail-open
- LLM self-judge
- unverified assumption
- unsafe repair
- incomplete rollback
- stale state
- broken provenance
- hardcoded environment
- README > implementation

---

## STEP 4 — REUSABLE

### 哪些能力可以合法复用？

分成：

```text
Direct Reuse
Adapt
Idea Only
Reject
```

同时记录：

- License
- Attribution
- 是否允许修改
- 是否允许商业用途
- 是否涉及第三方依赖

---

## STEP 5 — AEDL TRANSFORM

### 接入 AEDL 后，系统语义发生了什么变化？

这是最重要的一步。

不能只说：

> “我们加入了某项目的 XXX 功能。”

而应该写：

> **AEDL 对该能力做了什么重新定义。**

例如：

```text
CircuitBot Clarify
        ↓
AEDL Requirements Contract
        ↓
SHA256 Binding
        ↓
Intent
```

或者：

```text
KiCad MCP DRC
        ↓
AEDL Evidence Parser
        ↓
Semantic Gate
        ↓
Fault Injection
```

---

## STEP 6 — VERIFY

### 怎么证明吃进去以后真的更好了？

必须给：

- regression test
- fault fixture
- before / after
- failure case
- measurable improvement
- evidence artifact

否则：

> **没有验证的“吸收”，只是复杂度增加。**

# 9. AEDL 的项目叙事

以后不要再把项目描述成：

> “我们也做了一个 AI PCB Agent。”

更合适的技术叙事是：

> **AEDL 不以重复实现现有 AI EDA 能力为目标，而是在吸收现有开源生态成熟能力的基础上，重点解决硬件 Agent 在验证可信度、变更一致性、供应链约束、制造签发与经验闭环上的工程问题。**

再进一步：

> **生成能力不是最终目标。可信地证明设计为什么可以继续进入下一阶段，才是核心。**

```text
↓

↓

```

# 11. 第一阶段目标：先吃干净 CircuitBot Clarify

当前第一件真正值得落地的事情：

> **补齐 AEDL 的用户澄清闭环。**

目标不是复制 CircuitBot 的 clarify node。

而是形成：

```text
Natural Language
      ↓
Statement Extraction
      ↓
Ambiguity Detection
      ↓
Minimum Blocking Clarification
      ↓
User Answer
      ↓
Requirements Contract
      ↓
Contract Validation
      ↓
SHA256
      ↓
Intent
```

完成之后应新增：

```text
requirements_contract_v1.json
```

并建立对应 gate：

```text
requirements_contract_gate
```

至少检查：

- blocking question 不得未回答
- forbidden assumption 不得进入 intent
- intent 必须引用 contract
- contract 修改后旧 intent 自动失效
- contract hash 不一致 fail
- unresolved blocking item fail
- nonblocking assumption 必须显式记录

---

# 12. 最终原则

以后 AEDL 面对任何开源项目，只遵守三句话：

> **成熟的轮子，直接用。**

> **有缺陷的轮子，拆开修。**

> **真正没有的机制，集中火力自己造。**

最终目的不是证明：

> “每一个螺丝都是我们自己造的。”

而是证明：

> **我们知道哪些螺丝值得买，哪些结构必须自己设计，以及为什么整个系统最终比单个开源项目更可信。**

---

## 一句话版本

> **疯狂吸收，但绝不无脑拼装。复用工具，重构语义，验证一切。**
