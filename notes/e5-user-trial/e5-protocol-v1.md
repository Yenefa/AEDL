> 用途：W1 任务卡 **P2**（招募与准备）+ W5（执行）。对应矩阵实验 **E5「是否解决真实需求」**。
> 编制：Percy（`la4876949-bot`），2026-09-06（v1）；v1.1 修订：ZCode 主会话（Yenefa 授权），2026-09-08。状态：`PENDING_HUMAN_REVIEW`。
>
> **v1.1 修订动机（设计 blocker 更正，取代 v1 与五 PR 联合审计中"PR #40 无 blocker"的结论）**：
> v1 的「§0 两段式」把**全体基线放在第一段、全体 AEDL 放在第二段**（arm 与顺序完全混淆），
> §5 又声称「U-02 先 AEDL 后基线」的顺序交替——第一段根本没有 AEDL arm，该交错不可能成立。
> 带着 arm↔顺序混淆进入正式 E5 会让"两 arm 对比"失去内部效度，属**实打实的设计 blocker**，不应带入 E5。
>
> **v1.1 四项核心改动一览**：
> 1. 第一段访谈 = 正式数据；v1 的第一段 baseline 任务**降级为 exploratory**，不进入 E5 对照。

> 3. 两个 arm 统一 **outcome / timer / hint-intervention schema**（§5.3）。
> 4. 匿名（anonymous）→ **repository-pseudonymized**，补 **consent + human-review provenance**（§8）。

AEDL 的修复闭环当前**尚不可用**（Y2 akcli 适配、Y3 独立重验链路未完成），所以「用 AEDL 做任务」这一半现在做不了。但**前半段今天就能做**，而且不做会浪费已经到位的人。

| | 内容 | 时间 | 依赖 | 数据地位 |
|---|---|---|---|---|
| **第一段** | 背景登记 + 错误经历访谈（+ 可选 exploratory 基线任务，见 §4） | **现在起** | 无 | **访谈=正式数据**；exploratory 任务不进入 E5 对照 |
| **第二段** | **paired/counterbalanced 两 arm 对照**（baseline ↔ AEDL，同一批人） | W5（9/28–10/9） | Y2 + Y3 完成 | **E5 正式对照数据** |

**v1.1 与 v1 的关键区别**：v1 的第一段包含"基线任务计时"并直接称为 baseline——但它与第二段的 AEDL 任务**不同场次、不同任务、且第二段再无 baseline 复测**，两者不构成合法对照。v1.1 明确：**E5 的正式对照只来自第二段的两 arm**；第一段若做计时任务，仅作 exploratory（校准任务难度、估计用时量级、发现流程坑），**不得进入 E5 对照统计**。

**两段之间隔了时间，这是方法学上的让步，必须在报告里明写**，不能装作是同一场次的交错对照。矩阵原话是「尽可能交错顺序」——v1.1 下该让步**只影响访谈（时段 1）与两 arm 对照（时段 2）之间的关系**，两 arm 内部的顺序由 §5 的 counterbalancing 保证。

## 1. 招募（第一段，现在做）

### 1.1 对象标准

- **必须**：实际用 KiCad 画过至少一块板（打样与否不限）。
- **排除**：本项目成员、已了解 AEDL 的人、看过本文件的人。理由——他们知道我们想证明什么，数据会被污染。矩阵要求「外部试用与团队自测分别报告」。
- 目标 3–5 人。**3 人是下限**，低于 3 人只能作为个案记录，不进统计。
- **必须同时同意第二段**：v1.1 的 E5 正式对照来自第二段两 arm，只参加第一段的受访者其数据不进入 E5 对照（访谈仍可作 S1 证据）。招募时即按 §1.2 话术说明两段安排与知情同意（§8.1）。

### 1.2 招募话术（可直接发）

> 我在做一个开源的电子设计检查工具，想找几个用过 KiCad 的人聊 20 分钟，主要是问你以前画板子踩过什么坑、怎么发现的。
>
> 后面（大概 9 月底）如果方便，再花 30–40 分钟做两个小任务：一次用你现在的方法查错，一次用我们的工具查错，两次内容不同、难度相近，顺序随机安排。我们想对比的是用不用这个工具的差别，不是考你。
>
> 数据里不会出现你的名字和单位——只用编号代替，原始记录只存在我自己的电脑和这个学生竞赛项目的私有仓库里，竞赛材料中只出现汇总结果。不方便随时可以停，停止参与不需要任何理由。

**不要说的话**（会污染数据）：
- 不要说"帮我验证一下这个工具好不好用"——诱导正面反馈。
- 不要预先解释 AEDL 能查哪几类错——他们会照着答。
- 不要提 M2 的 USB 接反 / SHT30 地址事故——**这正是我们要看他们会不会自发提到的**。

### 1.3 完成条件

至少 **3 人口头确认**参与第一段，其中至少 3 人**明确同意参加第二段**（含 §8.1 知情同意要点：两段任务、逐字记录范围、pseudonymized 数据去向、随时退出权利）。

## 3. 访谈提纲（20 分钟，第一段核心）

**问法原则：先开放后具体。** 前 3 题不要提任何具体错误类型，看他自发说什么。

1. 你最近做的板子，**出过什么问题**？（不限电气/机械/制造）
2. 这个问题**是怎么发现的**？在哪个阶段？（画图时 / ERC / 打样后 / 焊完通电）
3. 从出错到发现，**大概隔了多久**？返工代价是什么（时间/钱/重新打样）？
4. 你**怎么检查**自己的板子？有没有固定流程或清单？
5. ERC / DRC 帮你抓到过什么？**有没有 ERC 全绿但板子还是错的情况**？
6. 你信不信 AI 帮你查电路？**什么情况下你会/不会信**？

**第 5 题是关键题。** 它直接对应 AEDL 的核心主张（"多份文件自洽 ≠ 正确"）。如果多数人从没遇到过"检查全过但板子错"，这个主张的普遍性就要打折扣。

### 3.1 必须记录的东西

- **逐字记下他自发提到的错误类型**（不要归类成我们的分类，先原样记）
- 是否**自发提到**跨视图问题（硬件↔固件不一致、引脚身份搞错、器件手册没看清）
- 明确的**不信任理由**（第 6 题）——这是产品设计输入，也是答辩会被问的

## 5. 第二段两 arm 对照设计（W5 执行；v1.1 重新设计，取代 v1 §5 草案）

> v1 的 §0/§5 是"第一段全体 baseline、第二段全体 AEDL"再声称顺序交替——自相矛盾且 arm↔顺序完全混淆。v1.1 改为**同场次 paired/counterbalanced** 设计。

### 5.1 设计要点

- **Paired within-subject**：同一人在**同一场次**（或至多相隔 48h 的两个场次，记录实际间隔）完成两个 arm 各一道题。
- **两 arm 任务难度相近但内容不同**——同一人在两个 arm 做不同题，避免记忆优势（矩阵：「不要重复同一道题造成记忆优势」）。
- **Counterbalanced by participant**（顺序在人之间平衡）：
  - 偶数编号（U-02、U-04）：**先 baseline 后 AEDL**；
  - 奇数编号（U-01、U-03、U-05）：**先 AEDL 后 baseline**；
  - 5 人时奇偶各 3/2，报告需注明顺序组合人数不平衡（3/2），并给出两方向各自的中位数。
- 顺序-任务配对（哪道题给哪个 arm）由**随机抽签**预先固定并记录（防"哪道题更难"与顺序系统性绑定）；每人的分配表存 `sessions/assignments.md`。
- **两 arm 之间休息 ≥10 分钟**；第一 arm 结束不讲解答案（防泄漏到第二 arm）。

### 5.2 两 arm 定义

| | **baseline arm** | **AEDL arm** |
|---|---|---|
| 工具 | 参与者现有方法（ERC/DRC + 自查，可上网查手册） | AEDL 检查流程（Y2+Y3 就绪后） |
| 任务 | 含 1 个已知缺陷的 KiCad 设计，**找到并说明问题** | 不同设计、同类缺陷难度 |
| 提示 | 无 | 无（AEDL 报告本身即工具输出，不加人工解释） |
| 计时 | 从拿到文件到给出结论 | 同左 |

- **缺陷类型从 P4 的 6 个开发案例抽取，两个 arm 用不同板子**（不用 M2 本体）。
- **每个 arm 两道题的难度配对由第一段 exploratory 数据校准**（这是 §4 保留 exploratory 的唯一用途）。

### 5.3 统一 outcome / timer / hint-intervention schema（两 arm 逐字段一致）

两 arm 的会话记录必须用**同一张表、同一套字段**（模板 `sessions/_TEMPLATE.md` v1.1 的「对照任务记录」节）：

| 字段 | 定义（两 arm 相同） |
|---|---|
| `outcome` | `found_exact`（定位并正确说明缺陷）/ `found_partial`（提到异常但归因错误）/ `not_found` / `abandoned`（中途放弃，原因必填） |
| `timer_start` / `timer_end` | 拿到文件 / 给出最终结论的时刻；**pause 事件单列**（去厕所、接电话等），净用时 = end − start − Σpause |
| `hint_events[]` | 每次外部介入一条：`{who: participant\|facilitator\|tool, what: 自由文本, at: mm:ss, phase: pre_conclusion\|post_conclusion}`。baseline arm 的"上网查手册"计入 hint_events（who=participant）；AEDL arm 的工具报告**不算 hint**（它是被测干预本身），工具之外的人工协助才算 |
| `interventions` | facilitator 主动干预次数（回答工具使用问题除外——使用问题属操作性支持，单列 `ops_questions` 计数） |
| `stuck_points` | 卡住的地方（原文） |
| `verbatim` | 口头吐槽原文 |

**hint/intervention 对称性检查**（报告时必须呈现）：两个 arm 的 facilitator 干预次数、ops_questions 计数并排报告，防"一个 arm 被多扶了一把"。

### 5.4 前置条件

Y2（akcli 适配）+ Y3（独立重验链路）可运行。**未达成则第二段不启动**，如实标未完成。

## 6. 记录与报告口径

- 原始记录存 `notes/e5-user-trial/sessions/`，文件名用编号（`U-01.md`），按 §8 的 pseudonymization 纪律执行。

## 8. 数据保护与 provenance（v1.1 新增）

### 8.1 知情同意（口头即可，记录要点）

招募与开场时向参与者说明并确认：

- [ ] 参与两段内容：①20 分钟访谈；②两段各约 30–40 分钟的任务对照
- [ ] 数据用途：仅用于学生竞赛 AEDL 的评测报告与答辩材料
- [ ] 记录范围：逐字笔记（不录音/录像，除非另行单独同意）
- [ ] 数据形态：**repository-pseudonymized**——使用 `U-01`…`U-05` 编号；不写真实姓名/联系方式/单位；不含可识别的项目名；竞赛材料只出现汇总
- [ ] 存储位置：个人电脑 + 项目**私有** GitHub 仓库（`Yenefa/AEDL`，repository-pseudonymized）；仓库公开前将再评估是否需要进一步脱敏（§8.2）
- [ ] 随时退出，不需要理由；退出前已收集的 pseudonymized 记录是否保留，由参与者选择

### 8.2 匿名等级更正：anonymous → repository-pseudonymized

v1 称"**全程匿名**"。严格说这在方法学上不成立：参与者与 facilitator（Percy）互相认识，招募由 Percy 私人联系，数据对 facilitator 不是匿名的。v1.1 更正为：

> **repository-pseudonymized**：仓库内仅出现编号与 pseudonymized 记录；真实身份只存在于 Percy 本人的线下通讯录，不入仓库、不入竞赛材料。

对参与者的描述一律用"编号代替、不记名字单位"的**通俗说法**（招募话术 §1.2 已按此措辞），文档与报告用 repository-pseudonymized 的**严格说法**，两者不矛盾。

### 8.3 human-review provenance

- 每份会话记录（`sessions/U-XX.md`）在**采集后 48h 内**由 Percy 通读一遍，文件头记录：
