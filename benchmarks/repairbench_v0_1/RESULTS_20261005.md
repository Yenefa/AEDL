## 未跑项与原因（如实）

`baseline_generic` / `aedl_contract` 两个 LLM 臂**未运行**。原因：本机唯一存在的
`ARK_API_KEY`（env 长度 46）对配置端点返回 **HTTP 401 Unauthorized**，对 RES-012 登记的
DeepSeek host 亦无有效凭据。按 ADR-022 决策 5 第 2 条，Agent 不自行动用他人账户或付费额度，
因此**没有跑出来的数字一律不写、不推测、不用「预计」代替**。

**因此当前不存在「AEDL 优于 baseline」的任何结论。** 一条都没有。

## 这次运行暴露的两个真问题

### 1. 冻结合同断言了器件**值**，却没断言**存在**（DC-03 / DC-04 / DC-05 全军覆没）

合同里 `ESP32_GPIO9_PULLUP` 写的是：

```json
"components": { "R9": { "value": "10k" } }
```

但这三集的故障恰恰是 **R9 / R7+R8 / C5 整个器件不存在**。机械臂据合同推出
「给 R9.1 加 `+3V3` 标签」，akcli 依法**拒绝**（exit 6，`pin reference 'R9' matches no
placed component`）。这是合同的**完备性缺口**，不是机械臂的缺陷：

> 合同能完整指定「某个已存在器件的某个脚应该接哪个网」，但**不能指定「这个器件应该被放上去」**——
> 缺 footprint、缺坐标、缺「必须存在」这一位。

影响：合同作为**修复说明书**目前只覆盖「改网名」类故障，覆盖不了「补器件」类故障。
这正是 v0.1 只有 5 集、单一板子时最容易漏掉的东西。

### 2. 按合同机械加标签会**合并已命名网络**（DC-01 结构性错，且被回归护栏抓到）

机械臂对 DC-01 推出两条标签，akcli 接受并写入，但结果是：

```text
net USB_DM: 期望 ['R8.2','U1.13']  实际 ['R7.2','R8.2','U1.13','U1.14']
net USB_DP: 期望 ['R7.2','U1.14']  实际 []
```

即 **DP 与 DM 被并成同一网**。原因：`add_net_label` 落在已属某网的脚上时，akcli 会按
strict-nets 语义处理；本次调用**没有加 `--strict-nets`**，于是命名网络被合并。

这一条是本次运行最有价值的产出：**Regression Guard + structural 两层同时把它抓住了**
（`structural: fail`，成员集合不符）。也就是说这套 benchmark 不只会给分，还能**指出失败原因**。

同时它给出一个明确的工程要求：**任何按合同推导标签的臂，都必须带 net-split 守卫**
（即 akcli 的 `--strict-nets`，或等价的事前拓扑差分检查），否则「修 A 弄坏 B」。

## 为什么 DC-01 的 primary 也是 FAIL

primary 要求 `USB_POLARITY_AND_SERIES` 由 fail 转 pass；该规则同时断言
`R7.1/R7.2/R8.1/R8.2/U1.13/U1.14` 六个脚的网名。机械臂只按「当前与合同不符」逐脚加标签，
在 DP/DM 已被并网的情况下无法让该规则整体转 pass。这与 oracle 的做法差别在于：
oracle 的答案还包含 2 条 `delete_object`，先清掉错误连线再重建。

## 结论（严格限于本次实测）

1. benchmark **可用**：有不可通吃的对照（noop 0/5）、有可解性对照（oracle 5/5）、
   三层指标都能给出方向性诊断。
2. 冻结合同作为修复说明书**不完备**：补器件类故障无法从合同推导（3/5 集）。
3. 按合同机械改网名**必须**配 net-split 守卫，否则会并网（DC-01 实测）。
4. **没有**任何 LLM 对比结果；**没有**任何「优于 baseline」的主张。
5. n=5、单板、netlist 作用域、离线。ADR-023 要求 20–30 集 / 3–5 故障族，v0.1 远未达到。

## 复现

py -3.9 -m tools.repairbench --arm noop
py -3.9 -m tools.repairbench --arm oracle
py -3.9 -m tools.repairbench --arm aedl_contract_deterministic

# 第二轮：两个 LLM 臂实跑（同模型 / 同任务 / 同产物 / 同预算）

## 凭据与预算

- 端点：`host=api.deepseek.com`，模型 `deepseek-v4-flash`（即 RES-012 已登记的 provider 与模型，
  **未新增任何第三方**）。凭据在运行时从本机 provider 配置读取，**不入仓库、不入日志、不入 argv**。
- 两个臂**完全对齐**：同一模型、同一 fixture、同一 artifact、同一写入器（akcli 0.21.0）、
  同一 `max_tokens`、同一单次预算（每集 1 次调用）。唯一差别是**模型能看到什么**：
  - `baseline_generic`：只给 pin/net 现状 + 一句故障描述，**不给合同**
  - `aedl_contract`：额外给冻结合同的 rule id / severity / source_ids / 期望 pin-net 意图
- 这正是 ADR-023 要求的 baseline 设计（"same model / task / artifact / budget / context"）。

## 结果矩阵（全部实跑）

| 配置 | `baseline_generic` | `aedl_contract` |
| --- | --- | --- |
| 无 net-split 守卫 | **3/5** | **3/5** |
| 加 `--strict-nets` | **2/5** | **2/5** |

逐集（无守卫时两臂完全一致）：

| episode | 目标规则 | 两臂结果 | 说明 |
| --- | --- | --- | --- |
| DC-02 | `SHT30_ADDRESS` | PASS | 合同足够简单，两臂都做对了 |
| DC-04 | `ESP32_GPIO9_PULLUP` | PASS | 补 R9 + 两标签，两臂都做对了 |
| DC-05 | `ESP32_EN_RC` | PASS | 补 C5 + 两标签，两臂都做对了 |
| DC-01 | `USB_POLARITY_AND_SERIES` | FAIL | **两臂以完全相同的方式并网** |
| DC-03 | `USB_POLARITY_AND_SERIES` | FAIL | baseline：写入器拒绝；aedl：模型返回空回复 |

## 结论 1：合同**没有**带来可测提升（null result）

两臂在两种配置下**逐集、逐分数完全相同**。在 n=5、单一板、单一故障族下，
**把冻结合同交给模型，没有产生任何可测收益**。

这是 null result，**不是**「差异很小」。如实写：目前**没有**任何证据支持
「冻结合同提升修复能力」这一主张。ADR-023 的 Kill Gate 假设 **H1**
（semantic contract 抓到 ERC/DRC 漏掉的 failure）在本轮**得不到支持**。

## 结论 2：并网风险被真实模型复现，不是机械臂的特例

DC-01 上两个臂产出**同样的并网损伤**：

```text
net USB_DM: expected ['R8.2','U1.13'] observed ['R7.2','R8.2','U1.13','U1.14']
net USB_DP: expected ['R7.2','U1.14'] observed []
```

`R7.2`（属 DP）与 `U1.14`（属 DP）被并进了 USB_DM。这与首轮机械臂的失败**同型**，
说明**任何只加标签、不带 net-split 守卫的臂都会踩**——它不是某一个臂的缺陷。

## 结论 3：`--strict-nets` 会**过度拦截**，代价是 1 集

加上守卫后，两臂都从 3/5 掉到 **2/5**，DC-02 从 PASS 变成**拒绝**：

```text
! MERGE GND + <unnamed@U2.2> -> GND
REFUSED: --strict-nets: net split/merge touches a named net; nothing written
```

即该守卫**无法区分**两种情形：
- DC-01：把 DP 与 DM 并成同一网 —— **真的危险，必须拦**
- DC-02：把一个悬空脚接到 GND —— **正是期望的修复，误拦**

所以守卫把「静默弄坏板子」换成了「安全地拒绝动手」。**这是正确的 fail-closed 行为，
但它不是 primary PASS**，本记录不把它算成成功。工程含义：需要**按 net 对的粒度**判断
「这次合并是否合法」，而不是一律按「碰到已命名网络即拒绝」。

## 本轮自身的两个 harness 缺陷（如实记录，均已修）

1. **`max_tokens` 预算不足**：首跑 DC-01/DC-03 返回**空回复**。原因是该模型为推理模型，
   思考 token 计入 `max_tokens`，2048 被思考吃光。已提到 **8192**，DC-01 随即恢复真实尝试
   （executed 4/5）。**这说明「预算对齐」必须包含推理模型的思考开销，否则对比不公平。**
2. **端点凭据解析**：`ARK_API_KEY` 对配置端点返回 401；实际可用凭据在本机 provider 配置里，
   已改为运行时解析（env 优先，回落本机配置），且**只输出 host / model / key 长度**。

## 严格边界

- 本轮**只有**这两个 LLM 臂、这一个模型、这 5 集。**不主张**任何模型间比较。
- 未与任何其它 agent / 工具比较；未做多轮 agent；未做 cost / latency 对比。
- n=5、单板、netlist 作用域投影（比父合同弱）、离线除模型调用外、不调 KiCad、不跑 ERC/DRC。
- **DC-03 在两臂下都不可执行**（一臂写入器拒绝、一臂空回复），该集**不计入分子也不计入分母的
  争议**：本记录按 `executed` 单列，未执行集不按 PASS 也未按 FAIL 计入 primary 分子。
